# 0013 — PROXY protocol за SNAT-шлюзом провайдера

Статус: принято (выбор владельца 2026-11-04); включается переменной `GOLEM_PROXY_PROTOCOL_FROM`, по умолчанию пусто (белый IP).

## Контекст
У части провайдеров VPS имеет серый IP: 443 приходит через шлюз с SNAT, и Caddy видит во всех соединениях адрес шлюза. Тогда rate limit и fail2ban (`caddy-ratelimit`) считают всех клиентов одним адресом: на prod (`golem01`) бан адреса шлюза закрыл 443 для всех. Провайдер включил на шлюзе PROXY protocol, и без ожидания заголовка Caddy обрывал соединения. Первичные правки на prod делались вручную (Q14).

## Решение
Один параметр `GOLEM_PROXY_PROTOCOL_FROM` (адреса/CIDR шлюза через пробел) → инвентори `proxy_protocol_from` (список). Из него выводятся оба эффекта:
- роль `caddy` (`caddy_proxy_protocol_from`): в `servers {}` блок `listener_wrappers { proxy_protocol { allow <адреса> } tls }`;
- роль `fail2ban` (`fail2ban_proxy_protocol_from`): адреса добавляются в `ignoreip` (бан шлюза недопустим: за ним все клиенты).
Пусто — блоков нет, рендер идентичен конфигурации для белого IP.

## Последствия
- Проверено на Lima (Caddy 2.x из `versions`): от разрешённого адреса с заголовком в логе подставленный клиентский IP; от разрешённого без заголовка — запрос обслуживается с реальным адресом соединения (локальные Gatus/health-check работают); от неразрешённого с заголовком — заголовок отбрасывается, IP остаётся адресом соединения (подделать нельзя); от неразрешённого без заголовка — обычное обслуживание.
- Клиентские IP в логе Caddy и в fail2ban — реальные; rate limit работает по клиенту, а не по шлюзу.
- Если шлюз — пул адресов, параметр принимает CIDR; но слишком широкий CIDR даёт доверие к чужим заголовкам и иммунитет к бану.
- Адрес шлюза не фиксируется в git (он в `mise.local.toml`).

## Пересмотреть
Если провайдер уберёт SNAT/PROXY protocol, сменит адрес шлюза (параметр надо обновить и прогнать `--tags caddy,fail2ban`) или для 443 появится прямой доступ.
